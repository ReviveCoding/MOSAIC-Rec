# Reference implementation compatibility (2026-09-20)

- [RecBole](https://github.com/RUCAIBox/RecBole) contains LightGCN, GRU4Rec, SASRec, and BERT4Rec. It declares broad Python/PyTorch floors, but [current compatibility work](https://github.com/RUCAIBox/RecBole/pull/2187) identifies NumPy 2, SciPy, `torch.load`, and Ray issues. Isolate and validate before parity claims.
- [MMRec](https://github.com/enoche/MMRec) includes VBPR, BM3 and FREEDOM. Its [requirements](https://github.com/enoche/MMRec/blob/master/requirements.txt) pin Python 3.7.11, PyTorch 1.11.0, NumPy 1.21.5, pandas 1.3.5 and SciPy 1.7.3. Do not merge these into the modern primary environment; use a separate reference environment or a tested port.
- [Original SASRec](https://github.com/kang205/SASRec) uses TensorFlow 1.12/Python 2. [Original LightGCN PyTorch](https://github.com/gusye1234/LightGCN-PyTorch) is archived and pins PyTorch 1.4. Use them as algorithmic references, not installed primary dependencies.
- [PyTorch official installation](https://pytorch.org/get-started/locally/) supports Linux Python 3.10 and CUDA wheels. Version and actual GPU operation will be recorded after environment qualification.

Runtime qualification: isolated `/home/bjw-0/mosaic-rec-work/ref-recbole` has RecBole 1.2.1, torch 2.14.0+cu130, NumPy 1.26.4, SciPy 1.13.1 and Ray 2.6.3. SASRec, GRU4Rec, BERT4Rec, and LightGCN modules imported successfully, and `torch.cuda.is_available()` returned true. This is an import smoke only; dataset loading, model training, checkpoint loading and metric parity remain unqualified.

The first full runtime attempt found three compatibility issues: Ray 2.6.3 imports removed `pkg_resources` (fixed in the isolated environment by pinning setuptools 80.9.0); RecBole's sequential `benchmark_filename` expects pre-augmented sequence fields, so a FIT-only atomic file with RecBole's internal leave-one-out split is used for smoke only; PyTorch >=2.6 defaults `torch.load` to weights-only and rejects RecBole's own checkpoint. The [official PyTorch environment variable](https://docs.pytorch.org/docs/main/miscellaneous_environment_variables.html) permits a narrowly scoped `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` for the checkpoint created by this smoke process. No external checkpoint is loaded. This smoke cannot establish protocol metric parity.

The final one-epoch RecBole SASRec CUDA smoke completed training, validation, checkpoint save/reload, and test evaluation. Its internal FIT-only leave-one-out validation NDCG@20 was 0.0053 and test NDCG@20 was 0.0026. These are **not** MOSAIC protocol results or parity comparisons; their users, items, split, loss and candidate semantics differ from the common evaluator. Receipt: `evidence/recbole_sasrec_smoke.json`.

No baseline parity is claimed until a common data role, candidate set, evaluation routine, seed policy and appropriate reference smoke have passed.

MMRec shallow reference checkout at commit `c68ee7c9b0de1ca7c5150258322edb4994be29d9` was inspected in WSL scratch. Its `requirements.txt` pins Python 3.7.11 and PyTorch 1.11.0, so it remains isolated from the primary environment. The BM3 reference's `full_sort_predict` scores graph/ID embeddings; its content vectors enter the training loss but not a content-only inference path. It must not be named the sole controlled-cold comparator. FREEDOM builds a content kNN item graph and may score FIT-hidden items through that graph, but its full pairwise item-similarity construction is O(items²); MicroLens 19,738 items is a feasible pilot target, while PixelRec 82,865 items exceeds the 16 GB GPU if built densely. Common-protocol parity and any cold-capability claim still require measurement.

MicroLens BM3 reference inputs were built from the already hash-qualified publisher vectors with an index-zero padding row required by MMRec; both padded arrays and source identities are recorded in `evidence/mmrec_micro_reference_input.json`. The reference's private SciPy DOK `_update` call is absent in SciPy 1.15; the local adapter assigns the same adjacency dictionary entries element by element without changing their values. `src/mosaic_rec/pilot_mmrec_bm3.py` is prepared for a one-epoch CUDA/common-validation runtime pilot, but no result is claimed until it runs. Reference model code remains in the separate WSL scratch checkout.

`src/mosaic_rec/pilot_mmrec_freedom.py` implements a one-epoch CUDA/common-validation runtime pilot using the same hash-qualified inputs. Its declared config is `configs/freedom_reference_pilot_p1.json`. The reference's dense cosine kNN constructor would divide by zero on the adapter-only item-zero padding row; the adapter computes the same cosine kNN over real item rows and adds an isolated padding self-edge. Real-item similarities and the reference k=10 choice remain unchanged. Attempt 1 started on CUDA, produced a hashed item graph cache, then disappeared without traceback, checkpoint or metric. Its cause is unknown and its interrupted receipt is retained. `configs/freedom_reference_attempt2_p1.json` declares a distinct diagnostic retry with identical feature hashes and a separate graph cache/output path. No FREEDOM score or cold-capability claim exists until a pilot runs and passes.

# BERT4Rec runtime follow-up

RecBole 1.2.1 BERT4Rec completed a one-epoch CUDA FIT-only train, checkpoint reload and internal evaluation smoke. Its internal NDCG@20 was 0.0028 validation and 0.0014 test. The split and candidate protocol differ from MOSAIC; these are **reference runtime checks only**, not parity or baseline scores. An unrelated GPU process appeared during the run, so wall time is invalid for throughput.

The [original BERT4Rec paper](https://arxiv.org/abs/1904.06690) defines bidirectional sequence modeling with Cloze masked-item prediction. The [RecBole 1.2.1 BERT4Rec source documentation](https://recbole.io/docs/_modules/recbole/model/sequential_recommender/bert4rec.html) shows masked-position training and an appended mask token for evaluation. A local common-protocol adaptation is prepared in `src/mosaic_rec/pilot_bert4rec.py`: it uses FIT-visible sequences, mandatory final-item masking plus random Cloze masks, full FIT-item softmax, and exact temporal validation catalog scoring. A CPU gradient test confirms a FIT-hidden cold item is absent from the training classes. It is **not** yet a measured pilot or reference/local parity result; architecture and loss details still require a declared parity audit after CUDA runtime qualification.
